# 1.9.6 Runtime Resource Audit

Local code audit and deterministic production-code tests, 2026-10-04.
CPU snapshot fix: `60944f5`. Comparison baseline: `v1.9.4`.
No HA instance or C300X was accessed. Counts below are simulated budgets,
not device CPU measurements or packet captures.

## Sampling and CPU Work

- The native monitor still samples every 30 seconds by default: 120 samples
  per hour. HTTP GETs and event-triggered snapshots reuse the completed sample.
- Each sample reads `/proc/stat`, `/proc/loadavg`, `/proc/meminfo`, and up to
  two thermal sysfs paths. The instance ID reads 16 bytes from `/dev/urandom`
  once at initialization. No process spawn or shell command in this path.
- The main loop sleeps until its earliest poll deadline. Failed delivery does
  not add a timer or an immediate retry loop; the next regular sample retries.
- HA sensors remain push-based. Concurrent recovery requests share one HTTP
  task. One expiry timer per entry marks stale data unavailable without I/O;
  unload cancels both resources. Retired agent IDs are bounded to 32.
- The existing high-CPU media watchdog remains enabled even without a metrics
  subscriber. It is not an idle polling mechanism added by this change.

## Traffic Budget

The production monitor test advances an hour in one-second steps, with a
previously acknowledged 1.0% sample and otherwise stable metrics:

| Scenario | Samples | Dispatch decisions | Metrics JSON bytes |
| --- | ---: | ---: | ---: |
| Stable readings, acknowledged | 120 | 6 | 2,828 |
| Alternating 1.0% / 1.1%, acknowledged | 120 | 119 | 56,064 |
| Stable readings, first heartbeat and all later deliveries fail | 120 | 101 | 47,593 |
| No metrics subscriber | 120 | 0 | 0 |

These are synthetic metric objects before event/HTTP/TCP framing, not wire
bytes. Core-count formatting depends on the test host. The regular-sampling
ceiling is 120 attempts per hour and matching subscriber at default settings;
registration and memo/message-change snapshots can add deliveries. The default
600-second heartbeat alone yields six attempts per hour. CPU precision is now
0.1 percentage point rather than a five-point threshold, so real traffic can
increase. This is the intentional cost of keeping the displayed value current.

Each webhook uses a fresh TCP connection (`Connection: close`). When MQTT is
enabled and connected, dispatched metrics also use the configured JSON event
topic; they have no raw OpenWebNet payload. Disabling metric sensor entities
does not disable the internal safety-event subscription.

## Writes and Memory

- Sampling, cached GET, callback acknowledgement and recent-event tracking do
  not write device files. Recent events are a bounded 16-entry RAM buffer.
  No persistent metric queue, subscription store or per-sample log is added.
- The test rejects any non-read `fopen` mode in the production sampler, verifies
  360 proc reads and 240 missing-temperature probes per simulated hour, and
  verifies that GET causes no additional reads.
- HA writes sensor state only when value, attributes or availability change.
  More accurate CPU updates can therefore create more Recorder entries, and
  changes to other metrics' attributes can also create entries. This is not
  zero HA database traffic. New sample IDs/ages are not sensor attributes.
- Configuration saves, maintenance operations and the existing sustained-CPU
  watchdog actions are separate explicit/event-driven write paths, not normal
  metric-sampling writes.
- Separately, the already committed PCMU change (`82f8884`) introduces an
  automatic patch attempt in `c300x_media_bridge_start`. With an unpatched
  PCMU device it can back up and replace the complete media executable and
  remount the root filesystem. An already patched target is read/verified but
  not rewritten. This path must not be described as globally write-free, and
  it does not increment the HTTP handler's `agent_write_count` counter.
- The corrected PCMU guard verifies complete file hashes and reads process
  names plus the matching `/proc/PID/exe` image at bridge startup and explicit
  codec-status/action requests. This adds firmware/proc reads, not a timer,
  network request or persistent activation marker. The metrics hot path and
  capabilities renderer do not perform these checks. Maintenance backfill now
  reports its write through the existing HTTP write counter.
- Capabilities rendering is now a pure serializer. The HTTP handler adds one
  in-memory video-status snapshot, no new firmware probe, timer or network
  request. Existing identity/bundle/firmware resolution remains unchanged.

## Remaining Risks

- Webhook delivery remains synchronous in the native main loop. A slow HA can
  block that loop during DNS, connect, send and response handling. The default
  socket timeout is 2,500 ms; this is not a total end-to-end deadline. The new
  status-line receive loop is bounded by a monotonic deadline and 63 bytes,
  but DNS and all send/connect phases do not share that deadline. More frequent
  updates expose this existing limitation more often. No speculative transport
  rewrite is included in the CPU fix.
- Local tests cannot establish actual C300X CPU percentage, physical flash
  writes by firmware/HA, or observed network volume. Device boot/GUI-restart
  comparison and an outage test remain necessary before a runtime claim.
- The three PCMU validation/activation findings have local regression fixes;
  see `1.9.6-review-v1.9.4.md`. This establishes the code's rejection and
  activation semantics, not that the 200-ms delay eliminates the device hang.
